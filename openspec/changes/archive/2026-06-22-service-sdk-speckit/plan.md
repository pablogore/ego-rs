# Implementation Plan: Service SDK

**Branch**: `008-service-sdk` | **Date**: 2026-06-08 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/008-service-sdk/spec.md`

## Summary

Define the Service SDK as a new `ego-service-sdk` crate providing a complete application-service layer — all transport-agnostic:

- **Service contracts** declared via `#[service]` trait attributes, plus `#[service]` struct attributes for implementations. Dual behavior: trait targets generate `ServiceDescriptor`, `OperationDescriptor`, `ContractDescriptor`; struct targets generate `DependencyMetadata`, `DependencyGraph`, `Injectable`, `RuntimeWiring` metadata.
- **Automatic descriptor generation** by the `ego-service-sdk-macros` proc-macro crate. Developers never write descriptors or dependency metadata manually.
- **Runtime-managed dependency resolution** through field-declared dependencies — services declare `EntityRef<T>`, `ServiceRef<T>`, read stores, configuration via annotated fields.
- **ServiceRef<T> generated type-safe proxies**. Invocations preserve trait ergonomics and compile-time method visibility (e.g., `orders.create_order(cmd).await?`). No string-based invocation. Proxies transparently apply ServiceContext scope, interceptor chains, and delegate to implementations.
- **Service registry** with type/name/version resolution, duplicate rejection, multi-module bundle merging, and startup-time dependency validation.
- **ServiceContext** propagated by the runtime via invocation scope (TaskLocal). Carries tenant ID, correlation ID, trace ID, deadline, timeout, cancellation token. ServiceContext::current() returns `Option<&ServiceContext>` — never panics outside invocation scope. Missing context is a valid runtime state (tests, CLI, migrations, background jobs work without it).
- **Runtime-enforced multi-tenant isolation** via TaskLocal scope. EntityRef<T> obtains context transparently — no API changes, no wrappers, no dependency on service-sdk types. Cross-tenant access requires explicit opt-in.
- **Optional invocation interceptors** (tracing, metrics, logging) attached at the registry boundary.
- **Hierarchical error model**: `DomainError` trait + `ErrorCategory` taxonomy; services define their own error types.
- **Deadline and cancellation propagation** across ServiceRef→ServiceRef→EntityRef chains without developer intervention.

### Developer Experience Goal

The SDK MUST support the following workflow without manual descriptor creation, manual dependency graphs, manual wiring, or string-based invocation:

```rust
#[service]
pub trait OrderService { /* operations */ }

#[service]
pub struct OrderServiceImpl {
    orders: EntityRef<Order>,
}

let runtime = EgoRuntime::builder()
    .with_entity::<Order>()
    .with_service::<OrderServiceImpl>()
    .build()
    .await?;
```

## Technical Design: ServiceRef Proxy Generation

**Decision**: `#[service]` proc-macro on traits generates a concrete named proxy type (`{TraitName}Ref`, e.g., `OrderServiceRef`) that implements the service trait. Resolution via the registry returns this generated proxy. The proxy holds a typed trait reference — no type erasure, no runtime downcasting.

**Why not a generic `ServiceRef<T>`**: Rust cannot dispatch trait method calls on `dyn Trait` without boxing every operation through an async trait object, which would lose type safety on method signatures. A concrete generated proxy type implements the trait directly and delegates each method call through the interceptor chain + context scope.

**Generated proxy structure** (per service trait):
```rust
// Generated by #[service] on trait OrderService
pub struct OrderServiceRef {
    inner: Arc<dyn OrderService>,           // typed trait reference — no Any, no downcast
    descriptor: &'static ServiceDescriptor,
    chain: Arc<InterceptorChain>,
}

#[async_trait]
impl OrderService for OrderServiceRef {
    async fn create_order(&self, cmd: CreateOrder) -> Result<OrderId, OrderError> {
        let ctx = ServiceContext::current();
        let op = /* operation descriptor for create_order */;
        self.chain.on_request(ctx.as_ref().unwrap_or(&/*empty*/), op).await;
        // Direct trait call — no reflection, no string dispatch, no operation lookup
        let result = self.inner.create_order(cmd).await;
        match &result {
            Ok(_) => self.chain.on_response(...).await,
            Err(e) => self.chain.on_error(..., e).await,
        }
        result
    }
}
```

**Resolution API**:
```rust
// Registry returns the generated proxy type — no dyn Trait exposed to caller
let orders = registry.resolve::<OrderService>(None, None)?;
// orders is typed as OrderServiceRef
orders.create_order(cmd).await?;
```

**Key properties**:
- **Trait-based invocation**: Every operation is called directly through the service trait. No string-based dispatch. No operation lookup by name. No reflection. Full compile-time method visibility and type checking.
- **Typed references**: `inner: Arc<dyn OrderService>` — the proxy holds the concrete service trait object, never `Arc<dyn Any>`. No runtime downcasting.
- **Clean resolution API**: `registry.resolve::<OrderService>()` returns `OrderServiceRef`. Callers never interact with `dyn Trait` directly. Registry consumers are unaware of proxy internals.
- **Minimal invocation overhead**: Each call executes ServiceContext scope entry + interceptor chain + trait delegation. Bounded runtime cost, not zero-overhead. Performance claims MUST remain verifiable.

**Design principles**:
- Service contracts ARE Rust traits, not dynamic command handlers.
- Compile-time safety is maximized; runtime reflection is minimized.
- The registry returns service handles, not implementation mechanics.

**Alternatives considered**:
- `Arc<dyn Any>` + downcast: Rejected — unnecessary type erasure, weakens compile-time guarantees, introduces reflection into the hot path.
- String-based `invoke("operation_name", input)`: Rejected — loses type safety, no compile-time method checking. Violates DX goal.
- `dyn OrderService` trait object directly (no proxy): Loses interception, context propagation, and tracing. Rejected — cross-cutting concerns must be transparent to service implementations.
