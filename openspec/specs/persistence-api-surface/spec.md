# Delta Specs: CORE-PERSIST-A — Unified Persistence API Surface (Domain-Owned Ports)

> Canonical / English. Spanish companion: `spec.es.md` (1:1 requirement IDs and scenarios).
> Single file covering two capabilities, per this change's Capabilities section: one new
> (`persistence-api-surface`) and one modified (`foundation-integrity`). This change is purely
> structural — no runtime behavior changes (OOS-6) — so every scenario is phrased in terms of
> compilation and identity, not runtime behavior.

## Capability: `persistence-api-surface` (NEW)

### Purpose

The observable contract that the domain-owned persistence port vocabulary — every trait,
error type, and contract type under `persistence/`, `read_side/`, and `operation/`, plus the
`DomainEvent` contract and the `id_type!` identity-macro generator — has exactly one owning
crate (`ego-persistence-api`), and that every path a consumer resolves today keeps resolving to
the same item after this change. This capability does not cover any implementation (in-memory
or Postgres adapters stay where they are) or any signature, SQL, or behavior change.

## Requirements

### Requirement: Every Relocated Item Moves Verbatim

The system MUST relocate every public item (trait, struct, enum, fn, type, const) declared in
the domain-owned `persistence/`, `read_side/{offset,dedup,store,projection_state_store,
event_tag,state,event_stream}`, and `operation/{reservation,key,receipt}` modules, plus the
`DomainEvent` contract (`event.rs`), into `ego-persistence-api`, unedited except for module
path.

#### Scenario: A trait relocates unedited
- GIVEN `OffsetStore` as declared in `ego_domain::read_side::offset` before this change
- WHEN it is located in `ego_persistence_api::read_side::offset` after this change
- THEN its declaration is identical except for the enclosing module path

#### Scenario: A bare constant relocates too, not only traits and structs
- GIVEN `operation::key::MAX_LEN` is a public constant, not a trait or struct
- WHEN the relocation completes
- THEN it resolves at `ego_persistence_api::operation::key::MAX_LEN` exactly as every other
  relocated item does

### Requirement: Old Path Resolves To The Same Item

Every item relocated by this change MUST remain resolvable, unedited, at its exact pre-change
`ego_domain::*` path, through a module-level re-export, and MUST resolve to the identical
item — not a re-declared item that merely shares a name.

#### Scenario: Unedited import still compiles
- GIVEN a crate compiling `use ego_domain::persistence::EventStore;` before this change
- WHEN it is compiled after this change with that statement unedited
- THEN it compiles, and the resolved trait identity-coerces with
  `ego_persistence_api::persistence::event_store::EventStore`

#### Scenario: An existing item-level re-export inside ego-domain still resolves
- GIVEN `ego_domain::persistence::mod.rs` republished `PersistenceError` at item granularity
  before this change
- WHEN the enclosing module becomes a module-level re-export of `ego-persistence-api`
- THEN `ego_domain::persistence::PersistenceError` still resolves, unedited, to the same type

### Requirement: Trait Shape Is Byte-Identical

Every relocated trait's method signatures, bounds, supertraits, and default bodies MUST be
identical before and after this change, differing only in module path.

#### Scenario: An async bound survives relocation
- GIVEN `EventStore<E: DomainEvent>` as declared before this change
- WHEN it is declared in `ego-persistence-api` after this change
- THEN its generic bound, method set, and `#[async_trait]` shape are unchanged

### Requirement: `Arc<T>` Forwarding Impls Move Intact

The `OffsetStore` and `DedupStore` blanket `Arc<T>` forwarding implementations MUST relocate
with their trait and MUST continue forwarding `is_durable()` to the inner store.

#### Scenario: A durable pair stays durable behind Arc
- GIVEN a store implementation whose `is_durable()` returns true
- WHEN it is registered behind `Arc<dyn OffsetStore>` after this change
- THEN `is_durable()` on the `Arc` still returns true, not the trait's default value

### Requirement: The `id_type!` Macro Relocates And Is Reinvoked, Not Duplicated

The `id_type!` macro MUST relocate to `ego-persistence-api` as `#[macro_export]`, generating
`TenantId`/`TenantIdError` there. `ego-domain` MUST generate its other five identity types by
re-invoking the relocated macro, not by duplicating its definition.

#### Scenario: `TenantId` resolves through the relocated generator
- GIVEN `TenantId` generated by the relocated `id_type!` macro
- WHEN it is resolved at `ego_domain::TenantId`
- THEN it is the exact type the relocated macro generated, not a second definition

#### Scenario: A non-relocated identity type still compiles from one generator
- GIVEN `AggregateId` is generated in `ego-domain` and is not itself relocated
- WHEN `ego-domain` compiles after this change
- THEN `AggregateId` is generated by invoking the re-exported macro, and only one `id_type!`
  definition exists workspace-wide

### Requirement: No Consumer Outside The Two Crates Is Edited

No crate other than `ego-domain` and `ego-persistence-api` MUST have an edited `use` statement
or an added `Cargo.toml` dependency as a result of this change.

#### Scenario: A downstream consumer compiles unedited
- GIVEN a crate importing a relocated item only through `ego_domain::*`
- WHEN the workspace is rebuilt after this change
- THEN that crate's source and `Cargo.toml` are byte-identical to before the change

### Requirement: `ego-persistence-api` Depends On No Workspace Crate

`ego-persistence-api` MUST NOT declare a `path` dependency on any other workspace crate,
including `ego-domain`.

#### Scenario: The new crate compiles in isolation
- GIVEN `crates/persistence-api/Cargo.toml`
- WHEN it is inspected
- THEN it names no workspace `path` dependency, and the crate builds standalone

### Requirement: Known-Dead Items Relocate Without New Behavior

`ProjectionStateStore` MUST relocate as-is, with zero implementations and zero consumers, and
MUST NOT gain an implementation or be deleted by this change.

#### Scenario: A dead trait stays dead after relocation
- GIVEN `ProjectionStateStore` has zero implementations before this change
- WHEN the workspace is searched for implementations after this change
- THEN it still has zero implementations, and it still resolves at its old path

## Non-Goals

- No SQL, migration, index, transaction, retry, or connection-pool change of any kind.
- No method-signature, async/sync, `Send`/`Sync`, or object-safety change to any relocated
  trait.
- No implementation move — every `InMemory*` and `PostgreSQL*`/`Postgres*` adapter stays in
  its current crate.
- No relocation of the `ego-runtime`-owned effect-store ports (`EffectStateStore`,
  `EffectDedupStore`, `RetentionMaintenance`) — deferred to a follow-up (F-1).
- No fix to `PostgreSQLRepository`'s confirmed tenant-scoping/`ON CONFLICT` defect — carried as
  named debt (F-2).
- No conformance harness added for `Repository`, `Snapshot`, `OffsetStore`, or `DedupStore`.

## Capability: `foundation-integrity` (MODIFIED)

## MODIFIED Requirements

### Requirement: FR-002 — Dependency Direction Enforcement

A crate's dependencies MUST NOT violate the documented layer direction: transport/
infrastructure MAY depend on domain and application only; application MAY depend on domain
only; domain MUST NOT depend on any other layer, EXCEPT that a domain-layer crate MAY depend
on another domain-layer crate (the domain self-edge).

(Previously: domain MUST NOT depend on any other layer, with no self-edge allowance — a
`domain` crate could depend on nothing at all, including another `domain` crate.)

#### Scenario: Wrong-direction dependency fails the gate
- GIVEN a crate in one layer depends on a crate in a layer the direction rules forbid
- WHEN the gate runs
- THEN it fails, identifying the offending crate and the violated direction rule

#### Scenario: A domain-to-domain self-edge passes the gate
- GIVEN a domain-layer crate depends on another domain-layer crate
- WHEN the gate runs
- THEN it passes for that edge, and no violation is reported for it

#### Scenario: Domain still cannot depend on foundation or infrastructure
- GIVEN a domain-layer crate depends on a foundation-layer or infrastructure-layer crate
- WHEN the gate runs
- THEN it still fails, identifying the offending crate and the violated direction rule
